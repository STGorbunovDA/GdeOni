ПЛАН РЕАЛИЗАЦИИ GdeOni
Сценарий: добавление умершего на могиле + хранение координат + отслеживание + маршрут

=====================================================================
A. ГЛАВНАЯ ЦЕЛЬ
=====================================================================

Реализовать полный пользовательский сценарий:

1. Пользователь физически находится у могилы.
2. Пользователь открывает приложение на смартфоне.
3. Пользователь нажимает кнопку "Добавить умершего".
4. Приложение запрашивает GPS-координаты телефона.
5. Пользователь разрешает доступ к геолокации.
6. Приложение получает:
   - latitude;
   - longitude;
   - accuracyMeters.
7. Пользователь видит точку на карте.
8. Пользователь может подтвердить точку или вручную поправить маркер.
9. Пользователь заполняет данные умершего:
   - имя;
   - фамилия;
   - отчество;
   - дата рождения;
   - дата смерти;
   - описание;
   - биография;
   - номер участка;
   - номер могилы.
10. Frontend отправляет запрос в backend.
11. Backend создаёт карточку умершего.
12. Backend сохраняет GPS-координаты как координаты могилы.
13. Backend автоматически добавляет этого умершего в список отслеживаемых текущего пользователя.
14. Пользователь может загрузить:
   - фото умершего;
   - фото могилы;
   - документы.
15. Позже пользователь открывает список отслеживаемых.
16. Пользователь выбирает умершего.
17. Пользователь нажимает "Построить маршрут".
18. Приложение получает текущие координаты пользователя.
19. Backend возвращает координаты могилы и ссылки для карт.
20. Frontend строит маршрут или открывает внешний сервис карт.

Главное правило разработки:

1. Сначала полностью делаем backend.
2. Потом покрываем backend тестами.
3. Потом проверяем полный backend-сценарий вручную.
4. Только после этого начинаем frontend.

Почему именно так:

Frontend зависит от backend API.
Если начать frontend раньше, придётся постоянно переписывать формы, DTO, обработку ошибок и маршруты.
Поэтому сначала нужно стабилизировать backend-контракты.

B. ТЕКУЩАЯ АРХИТЕКТУРА ПРОЕКТА
=====================================================================

Проект построен на .NET 8 и Clean Architecture.

Основные проекты:

1. backend/src/GdeOni.Domain
2. backend/src/GdeOni.Application
3. backend/src/GdeOni.Infrastructure
4. backend/src/GdeOni.API

---------------------------------------------------------------------
B1. Domain
---------------------------------------------------------------------

Domain — это ядро проекта.

В Domain должны находиться:

- сущности;
- value objects;
- enum;
- доменные методы;
- бизнес-инварианты;
- правила, которые не зависят от базы данных, API или frontend.

Примеры:

- Deceased;
- BurialLocation;
- User;
- TrackedDeceased;
- DeceasedMedia;
- LifePeriod;
- PersonName.

В Domain нельзя добавлять:

- EF Core DbContext;
- HTTP-зависимости;
- controllers;
- MinIO SDK;
- IConfiguration;
- внешние API-клиенты.

Правило:

Domain должен оставаться чистым.
Если завтра поменяется PostgreSQL на другую базу или MinIO на S3, Domain не должен измениться.

---------------------------------------------------------------------
B2. Application
---------------------------------------------------------------------

Application — слой бизнес-сценариев.

В Application должны находиться:

- use cases;
- commands;
- queries;
- DTO;
- validators;
- interfaces для инфраструктуры;
- application services.

Примеры:

- AddDeceasedAtGraveUseCase;
- GetTrackedDeceasedUseCase;
- UploadMediaUseCase;
- GetRouteToGraveUseCase;
- IFileStorage;
- IRouteLinkProvider;
- ICurrentUserService;
- IDeceasedRepository;
- IUserRepository.

Application знает, что нужно сделать, но не знает технических деталей.

Например:

Application знает, что файл нужно загрузить через IFileStorage.
Но Application не знает, что внутри используется MinIO.

Application знает, что нужно получить текущего пользователя.
Но Application не должен напрямую читать HttpContext.

---------------------------------------------------------------------

В Infrastructure должны находиться:

- EF Core;
- AppDbContext;
- repositories;

- migrations;
- MinIO implementation;
- routing link providers;

Примеры:

---------------------------------------------------------------------
B4. API
---------------------------------------------------------------------

API — внешний слой приложения.

В API должны находиться:

- controllers;
- middleware;
- swagger;
- authentication setup;
- authorization setup;
- DI registration;
- Program.cs;
- request/response mapping, если это не часть Application.

Контроллеры не должны содержать бизнес-логику.

Контроллер должен:

1. Принять HTTP request.
2. Передать данные в use case.
3. Получить result.
4. Вернуть HTTP response.

Плохо:

Контроллер сам создаёт Deceased, сам проверяет права, сам пишет в DbContext.

Хорошо:

Контроллер вызывает AddDeceasedAtGraveUseCase.

---------------------------------------------------------------------
C1. Deceased
---------------------------------------------------------------------

Deceased — карточка умершего.

Она должна хранить:

- Id;
- имя;
- фамилию;
- отчество;
- дату рождения;
- дату смерти;
- краткое описание;
- биографию;
- место захоронения;
- координаты могилы;
- автора записи;
- статус подтверждения;
- search key;
- медиафайлы;
- воспоминания.

Главное изменение:

BurialLocation должен стать nullable.

Причина:

Не всегда у пользователя есть полный адрес захоронения.
В сценарии "пользователь стоит у могилы" у него часто есть только GPS-координаты со смартфона.

Примеры допустимых состояний:

1. Умерший создан с полным местом захоронения:
   - Country;
   - City;
   - CemeteryName;
   - PlotNumber;
   - GraveNumber;
   - Latitude;
   - Longitude.

2. Умерший создан только с GPS:
   - Latitude;
   - Longitude;
   - AccuracyMeters.

3. Умерший создан вообще без BurialLocation:
   - место будет добавлено позже.

Domain-правила:

- Deceased должен уметь существовать без BurialLocation.
- Если BurialLocation есть, координаты должны быть валидными.
- SearchKey не должен падать, если BurialLocation == null.
- Автор записи должен сохраняться через CreatedByUserId.
- Изменение BurialLocation должно происходить через доменный метод.

---------------------------------------------------------------------
C2. BurialLocation
---------------------------------------------------------------------

BurialLocation — value object места захоронения.

Должен хранить:

- Latitude;
- Longitude;
- AccuracyMeters;
- Country;
- City;
- CemeteryName;
- PlotNumber;
- GraveNumber.

Новые правила:

- Latitude обязателен, если BurialLocation создан.
- Longitude обязателен, если BurialLocation создан.
- Latitude должен быть от -90 до 90.
- Longitude должен быть от -180 до 180.
- AccuracyMeters должен быть >= 0, если передан.
- Country больше не обязателен.
- City больше не обязателен.
- CemeteryName больше не обязателен.
- PlotNumber опционален.
- GraveNumber опционален.

Нужный factory method:

BurialLocation.CreateFromGps(latitude, longitude, accuracyMeters)

Этот метод нужен для сценария со смартфоном.

Пример:

Пользователь стоит у могилы.
Телефон возвращает:

latitude = 55.7558
longitude = 37.6173
accuracyMeters = 8.5

Backend создаёт BurialLocation без Country и City, но с координатами.

---------------------------------------------------------------------
C3. User
---------------------------------------------------------------------

User — пользователь системы.

Должен хранить:

- Id;
- Email;
- UserName;
- FullName;
- Role;
- TrackedDeceased;
- RefreshTokens.

Основные задачи User:

- хранить профиль пользователя;
- хранить роль;
- хранить список отслеживаемых умерших;
- уметь добавить умершего в отслеживаемые;
- уметь убрать умершего из отслеживаемых;
- уметь обновить настройки отслеживания.

В будущем User также должен хранить refresh tokens.

---------------------------------------------------------------------
C4. TrackedDeceased
---------------------------------------------------------------------

TrackedDeceased — связь пользователя с конкретным умершим.

Должен хранить:

- Id;
- UserId;
- DeceasedId;
- RelationshipType;
- PersonalNotes;
- NotifyOnDeathAnniversary;
- NotifyOnBirthAnniversary;
- Status;
- TrackedAtUtc.

Статусы:

- Active;
- Muted;
- Archived.

Главное правило:

Когда пользователь добавляет умершего на могиле через AddDeceasedAtGrave, backend должен автоматически создать TrackedDeceased для текущего пользователя.

Почему:

Если пользователь сам добавил умершего на могиле, логично, что эта запись сразу появляется у него в списке отслеживаемых.
Не нужно заставлять пользователя отдельно нажимать "Отслеживать".

---------------------------------------------------------------------
C5. DeceasedMedia
---------------------------------------------------------------------

DeceasedMedia — универсальная сущность файлов.

Она должна заменить старый подход, где фото хранится просто как URL.

DeceasedMedia должна поддерживать:

- фото умершего;
- фото могилы;
- документы;
- прочие файлы.

Поля:

- Id;
- DeceasedId;
- UploadedByUserId;
- Kind;
- OriginalFileName;
- Bucket;
- StorageKey;
- ContentType;
- SizeBytes;
- Description;
- IsMainPhoto;
- ModerationStatus;
- CreatedAtUtc;
- UpdatedAtUtc.

MediaKind:

- DeceasedPhoto;
- GravePhoto;
- Document;
- Other.

Правила:

- DeceasedPhoto может быть главным фото.
- GravePhoto не должно быть главным фото карточки умершего.
- Document не может быть главным фото.
- У одного Deceased может быть только одно главное DeceasedPhoto.
- Документы должны быть приватными.
- Фото могут быть публичными для чтения.
- Binary-файл хранится в MinIO.
- Metadata файла хранится в PostgreSQL.

[ ] После logout refresh не работает.

D1.6 UniqueConstraintException -> 409
---------------------------------------------------------------------

Если возникает конфликт уникальности, API не должен возвращать 500.

Примеры конфликтов:

- email уже существует;
- username уже существует;
- search key уже существует;

Нужно возвращать:

Пример:

{

  "errorMessage": "Пользователь с таким email уже существует."
}

Готово, если:

[ ] Дубликат email возвращает 409.
[ ] Дубликат username возвращает 409.
[ ] Ошибка не уходит в ExceptionMiddleware как 500.
[ ] Frontend получает понятный errorCode.

=====================================================================
D3. ADD DECEASED AT GRAVE
=====================================================================

Цель:

Сделать главный сценарий одним backend-запросом.

Endpoint:

POST /api/deceased-records/at-grave

---------------------------------------------------------------------
D3.1 Request
---------------------------------------------------------------------

Запрос должен принимать:

- firstName;
- lastName;
- middleName;
- birthDate;
- deathDate;
- shortDescription;
- biography;
- graveLocation;
- tracking.

graveLocation:

- latitude;
- longitude;
- accuracyMeters;
- country;
- city;
- cemeteryName;
- plotNumber;
- graveNumber.

tracking:

- relationshipType;
- personalNotes;
- notifyOnDeathAnniversary;
- notifyOnBirthAnniversary.

---------------------------------------------------------------------
D3.2 Response
---------------------------------------------------------------------

Успешный ответ:

HTTP 201 Created

{
  "deceasedId": "...",
  "trackingId": "...",
  "trackingStatus": "Active"
}

---------------------------------------------------------------------
D3.3 Use case logic
---------------------------------------------------------------------

AddDeceasedAtGraveUseCase должен делать:

1. Взять currentUserId из JWT.
2. Проверить, что пользователь авторизован.
3. Загрузить User вместе с TrackedDeceased.
4. Создать BurialLocation через CreateFromGps.
5. Создать Deceased.
6. Добавить Deceased в DeceasedRepository.
7. Вызвать user.TrackDeceased(deceased.Id, ...).
8. Сделать один SaveChanges.
9. Вернуть deceasedId и trackingId.

---------------------------------------------------------------------
D3.4 Atomicity
---------------------------------------------------------------------

Важно:

Deceased и TrackedDeceased должны создаваться атомарно.

Нельзя:

1. Save Deceased.
2. Save Tracking.

Нужно:

1. Add Deceased.
2. Add Tracking.
3. Один SaveChanges.

Если tracking не создался, Deceased не должен сохраниться.

Готово, если:

[ ] Deceased и TrackedDeceased сохраняются вместе.
[ ] При ошибке tracking Deceased не появляется в БД.
[ ] При ошибке SaveChanges не остаётся половинчатых данных.

---------------------------------------------------------------------
D3.5 Validation
---------------------------------------------------------------------

Проверить:

- firstName обязателен;
- lastName обязателен;
- deathDate обязателен;
- deathDate не в будущем;
- birthDate не позже deathDate;
- latitude от -90 до 90;
- longitude от -180 до 180;
- accuracyMeters >= 0;

D7.7 MIME validation по magic numbers
---------------------------------------------------------------------

Сейчас FileValidator проверяет только Content-Type из multipart-заголовка.
Это значение присылает клиент, его можно подделать.
Можно загрузить .exe под видом image/jpeg.

Нужно валидировать тип файла по первым байтам потока:

- JPEG: FF D8 FF;
- PNG: 89 50 4E 47 0D 0A 1A 0A;
- WebP: RIFF .... WEBP;
- PDF: 25 50 44 46.

Логика:

1. Прочитать первые 12 байт из request.Content.
2. Сравнить с сигнатурой по FileKind.
3. Если не совпадает — вернуть Errors.Media.PhotoContentTypeNotAllowed
   или DocumentContentTypeNotAllowed.
4. Сбросить позицию потока на 0 перед UploadAsync.

Важно:

- проверка по магическим байтам должна быть в Application (FileValidator),
  а не в Infrastructure;
- поток должен быть seekable, либо буферизуемым через MemoryStream;
- для multipart IFormFile это уже выполняется (поток seekable).

Готово, если:

[ ] FileValidator принимает Stream и сверяет первые байты.
[ ] .exe с Content-Type image/jpeg отклоняется.
[ ] PDF с Content-Type image/png отклоняется.
[ ] Позиция потока после проверки сброшена на 0.
[ ] Существующие фото и PDF продолжают грузиться.

D7.8 Presigned URL для production
---------------------------------------------------------------------

Сейчас MinioFileStorage.GetPresignedUrlAsync генерирует ссылку через
IMinioClient, который сконфигурен на MinioOptions.Endpoint.
В production endpoint = "minio:9000" — внутренний адрес контейнера,
не доступный из браузера.

Получится presigned URL вида http://minio:9000/... — он не сработает
ни на каком фронтенде.

Нужно либо:

A. Использовать MinIO server-side переменную MINIO_SERVER_URL
   (рекомендуется): MinIO сам подставляет публичный host в presigned URL.

B. Настроить второй IMinioClient (publicClient) на PublicBaseUrl
   и использовать его только для GetPresignedUrlAsync.

C. После генерации ссылки заменить host на PublicBaseUrl.

Документация по варианту A:

- docker-compose: добавить env MINIO_SERVER_URL=https://files.example.com;
- nginx: проксировать на minio:9000;
- TLS termination на nginx.

Готово, если:

[ ] В production presigned URL содержит публичный домен.

[ ] В docker-compose описана переменная MINIO_SERVER_URL.

D7.9 Сброс IsMainPhoto при reject и delete
---------------------------------------------------------------------

Сейчас DeceasedMedia.Reject() меняет только ModerationStatus.
Если админ отклонил главное фото, оно остаётся IsMainPhoto = true.
GetMainPhoto() продолжает его возвращать, в карточке светится
mainPhotoUrl от rejected-файла.

То же самое для DeleteMedia: если удалили main photo, у Deceased
больше нет main photo, что ОК, но если осталось другое DeceasedPhoto,
оно не становится автоматически новым main.

Поведение:

- Reject main photo -> IsMainPhoto = false. Никакое другое фото
  не становится main автоматически (это решение пользователя).
- Delete main photo -> главное фото пропадает. Никакое другое фото
  не становится main автоматически.

Готово, если:

[ ] DeceasedMedia.Reject сбрасывает IsMainPhoto если он был true.
[ ] Deceased.RemoveMedia корректно удаляет main photo
    (ничего не назначает автоматически).
[ ] GetMainPhoto не возвращает rejected-файл.
[ ] Юнит-тест Domain покрывает оба сценария.

D7.10 Cleanup orphan files в MinIO
---------------------------------------------------------------------

При удалении карточки Deceased EF делает Cascade на deceased_media,
но физические файлы в MinIO остаются как сироты.

Когда появится use case DeleteDeceased, нужно перед SaveChanges
собрать все (Bucket, StorageKey) media этого Deceased и удалить их
из MinIO best-effort после успешного Save.

Дополнительно — фоновая задача-чистильщик:

- раз в сутки;
- листать MinIO bucket;
- сверять storage_key с БД;
- если ключа нет в deceased_media — удалять из MinIO старше 24 часов
  (защита от race с Upload, который ещё не успел сделать SaveChanges).

Готово, если:

[ ] DeleteDeceasedUseCase удаляет media из MinIO перед/после SaveChanges.
[ ] Best-effort: ошибка MinIO логируется, не блокирует удаление в БД.

D7.17 Logout — анонимный отзыв чужого токена (DoS / IDOR)

POST /api/auth/logout не имеет [Authorize] на action или контроллере.

D7.32 Refresh token replay не детектится

переавторизуется. Компрометация остаётся незамеченной — ничьи токены
не отзываются, журнал безопасности молчит.

revoke всю «семью» токенов пользователя + log warning + потенциально
форс-логаут (через RevokeAllForUser, тогда SecurityStamp не меняется,
но все RT уйдут в revoke; access-токены живут до expire).

Решение:
- Добавить колонку replaced_by_token_hash в refresh_tokens.
- При rotate в RefreshUseCase записывать new.Hash в old.ReplacedByTokenHash.
- Новый Errors.RefreshToken.ReplayDetected.
- В RefreshUseCase: если existingToken.IsRevoked → не просто вернуть
  TokenRevoked, а вызвать refreshTokenRepository.RevokeAllForUser(userId)
  и log.LogWarning с user_id, ip, ua.

Готово, если:

[ ] Replay revoked токена приводит к revoke всех активных RT юзера.
[ ] В Seq фиксируется warning с user_id и client IP.
[ ] Тест-сценарий «refresh → refresh-снова-старым-токеном» возвращает 401

D7.45 Pending/Rejected фото публично доступны по прямому URL

public-read policy (см. BuildPublicReadPolicy в MinioBootstrap.cs).

- URL утекает в preview автору / в moderation UI / в шаре ссылки.

   с public URL — предполагается, что между upload и Approve проходят
   минуты, риск приемлем.
2. **Строгое:** держать все фото в private bucket с presigned URL до
   Approve. После Approve — copy в public bucket. Сложнее, требует
   двух bucket'ов на kind и переноса при модерации.

Рекомендую (1) как mvp.

[ ] Reject фото удаляет файл из MinIO в том же use case (best-effort).
[ ] Лог warning при провале удаления — не блокируем reject.

D7.46 Memory-операции линейно сканируют коллекцию
---------------------------------------------------------------------

UpdateMemoryUseCase, ApproveMemoryUseCase, RejectMemoryUseCase,
RemoveMemoryUseCase — все используют GetByIdWithMemories, потом
вызывают доменный метод (EditMemory / ApproveMemory / etc), который
делает `_memories.FirstOrDefault(x => x.Id == memoryId)`.

Для одной операции тянем всю коллекцию воспоминаний. На карточке
с сотнями записей — лишний RAM/трафик.

Сложность фикса: Memory часть aggregate root Deceased (DDD), доменные
методы вызываются на корне. Нельзя просто загрузить один memory без
загрузки агрегата — нарушение invariant'ов.

Решение:
- Добавить в IDeceasedRepository метод `GetByIdWithMemoryById(deceasedId, memoryId, ct) → Deceased?`
  — Include с Filtered (`.Include(x => x.Memories.Where(m => m.Id == memoryId))`).
  EF Core 5+ поддерживает filtered include, грузит только одну строку.
- Use case'ы переключить на новый метод. Domain методы (EditMemory etc)
  работают как раньше — `_memories.FirstOrDefault` находит единственный
  загруженный элемент.
- GetByIdWithMemories оставить для read-сценариев (GetById, GetMyTrackedDeceasedDetails),
  где нужны все memories.

Trade-off: если вызвать filtered Include и memory не найден — `_memories`
пуст, `EditMemory` вернёт NotFound, что корректно.

Готово, если:

[ ] Update/Approve/Reject/RemoveMemory используют GetByIdWithMemoryById.
[ ] EF транслирует Include с Where в SQL `LEFT JOIN deceased_memory_entries
    ON ... AND memory_id = @memoryId`.

D7.54 Password без MaximumLength — потенциальный DoS через BCrypt
---------------------------------------------------------------------

[RegisterUserCommandValidator.cs:32-36](backend/src/GdeOni.Application/Users/Commands/Register/Validation/RegisterUserCommandValidator.cs#L32-L36)
и [ChangePasswordCommandValidator.cs:17-21](backend/src/GdeOni.Application/Users/Commands/ChangePassword/Validation/ChangePasswordCommandValidator.cs#L17-L21):

```csharp
RuleFor(x => x.Password)
    .NotEmpty()
    .WithError(Errors.User.PasswordRequired())
    .MinimumLength(PasswordPolicy.MinPasswordLength)
    .WithError(Errors.User.PasswordTooShort(PasswordPolicy.MinPasswordLength));
```

Нет `MaximumLength`. ASP.NET Core по умолчанию принимает JSON body до
~30MB. Атакующий может слать ChangePassword/Register с 10MB-полем
Password. BCrypt.Net по спецификации обрежет до 72 байт, но до
обрезки .NET аллоцирует на heap всю строку, JSON-deserializer читает
её, плюс `Encoding.UTF8.GetBytes()` внутри BCrypt тратит CPU.
Rate-limit auth-политики (D7.39, 10/мин) ограничивает частоту, но
один запрос всё равно тратит CPU+RAM не за пик нагрузки.

CurrentPassword в ChangePasswordUseCase передаётся в `Verify` — там
BCrypt тоже срежет, но поверх та же тропинка с heap-аллокацией.

Решение:
- Добавить `PasswordPolicy.MaxPasswordLength = 128` (типичная политика
  в Identity/ASP.NET Core; bcrypt всё равно режет до 72 байт, 128
  дают запас под пасс-менеджеры с длинными паролями).
- В RegisterUserCommandValidator: `.MaximumLength(PasswordPolicy.MaxPasswordLength)
  .WithError(Errors.User.PasswordTooLong(PasswordPolicy.MaxPasswordLength))`.
- То же в ChangePasswordCommandValidator (для NewPassword).
- Добавить `Errors.User.PasswordTooLong(int maxLength)` в Errors.cs.
- Опционально: добавить правило для CurrentPassword (без NotEmpty,
  только MaximumLength), чтобы и оно не пропускало мегабайтные строки.

Готово, если:

[ ] PasswordPolicy.MaxPasswordLength = 128.
[ ] Register/ChangePassword падают на 400 для Password длиннее 128.
[ ] Errors.User.PasswordTooLong существует.

D8.11 DeceasedDetailsResponse.Memories без OrderBy — недетерминированный порядок
---------------------------------------------------------------------

[DeceasedRecordsResponseMapping.ToDetailsResponse](backend/src/GdeOni.API/Mappers/DeceasedRecordsResponseMapping.cs#L84)
проецирует `deceased.Memories` в response без явной сортировки.
Порядок зависит от того, как EF загрузил коллекцию: при `Include`
без `OrderBy` PostgreSQL может возвращать строки в любом порядке
(в практике — по физическому heap-storage / page-id, что меняется
после VACUUM / UPDATE).

Симптом для клиента: повторные `GET /api/deceased-records/{id}`
могут возвращать воспоминания в разном порядке между запросами.

Решение:
- В `DeceasedRecordsResponseMapping` сортировать
  `memoriesQuery.OrderBy(m => m.CreatedAtUtc)` перед `Select`;
- Альтернативно — добавить sort на уровне репозитория
  (`Include(d => d.Memories.OrderBy(m => m.CreatedAtUtc))`),
  но в EF8 это требует extra setup'а; для presentation-stability
  достаточно sort'а в маппере.

Готово, если:

[ ] Два подряд GET'а на одну карточку возвращают memories в одном
    порядке (по CreatedAtUtc ASC).
[ ] Build clean.

- `MediaDetailsResponse.ModerationStatus` отдаётся `media.ModerationStatus.ToString()`;
- `MediaListItemResponse.ModerationStatus` — то же.

Контракт расходится: для одной и той же `ModerationStatus` enum
клиент в одном эндпоинте получает `0` / `1` / `2`, в другом —
`"Pending"` / `"Approved"` / `"Rejected"`. Магические числа на
клиенте → frontend ломается при добавлении нового value enum'а.

Решение:
- Поменять `(int)memory.ModerationStatus` →
  `memory.ModerationStatus.ToString()`;
- В `DeceasedMemoryResponse.ModerationStatus` тип сменить с `int`
  на `string`.

Готово, если:

[ ] grep `(int)memory.ModerationStatus|(int)x.ModerationStatus`
    по `src/` ничего не находит;
[ ] `DeceasedMemoryResponse.ModerationStatus` имеет тип `string`;
[ ] Manual проверка: GET карточки с memory отдаёт строковый статус.

---------------------------------------------------------------------
D8.13 UserRepository.ExistsBy* без AsNoTracking
---------------------------------------------------------------------

[UserRepository.ExistsByEmail / ExistsByUserName / ExistsById](backend/src/GdeOni.Infrastructure/Persistence/Repositories/UserRepository.cs#L77)
используют `AnyAsync` без `.AsNoTracking()`. Эти методы вызываются
из read-only-сценариев (Register / ChangeEmail / UpdateProfile /
DeleteUser). `AnyAsync` сам по себе не материализует сущность
(EXISTS-subquery в SQL), но на default-tracking-режиме EF
аллоцирует change-tracker entries даже под промежуточные операции.

Аналог DeceasedRepository.ExistsById, который уже сделан с
`AsNoTracking()`. Для согласованности и микро-perf'а — выровнять.

Решение:
- В трёх методах `ExistsBy*` поставить `.AsNoTracking()` перед
  `AnyAsync` (или перед `Where`).

Готово, если:

[ ] grep `AnyAsync` по UserRepository не находит вызовов без
    AsNoTracking (за исключением `IsActivelyTracking`, где
    AsNoTracking уже стоит).
[ ] Build clean.

E3. Добавление умершего на могиле
---------------------------------------------------------------------

UI flow:

1. Пользователь нажимает "Добавить умершего".
2. Frontend вызывает navigator.geolocation.getCurrentPosition.
3. Браузер запрашивает разрешение.
4. Если пользователь разрешил — получаем координаты.
5. Показываем карту.
6. Показываем маркер.
7. Пользователь может поправить маркер.
8. Пользователь заполняет форму.
9. Frontend отправляет POST /api/deceased-records/at-grave.
10. После успеха frontend переходит на карточку умершего.

Важно:

- на production нужен HTTPS;
- на localhost работает без HTTPS;
- пользователь может запретить геолокацию;
- accuracy может быть плохой;
- нужно дать возможность поправить точку вручную.

F. SECURITY RULES
=====================================================================

F1. userId брать только из JWT.

F2. Не принимать userId из body, query или route для пользовательских операций.

F3. Все пользовательские endpoints делать через /me.

F4. Проверки прав делать в use case, а не только через атрибуты контроллера.

F5. Координаты от смартфона хранить вместе с AccuracyMeters.

F6. Не считать GPS абсолютно точным.

F7. Загружаемые файлы проверять по:
- MIME;
- extension;
- size;
- magic numbers, если возможно.

F8. Документы не делать public.

F9. Фото можно сделать public read.

F10. Refresh token хранить только как hash.

F11. Plain refresh token не хранить в БД.

F12. Secrets не хранить в git.

F13. Бизнес-ошибки не должны возвращать 500.

F14. 401 использовать для неавторизованных.

F15. 403 использовать для запрета доступа.

F16. 409 использовать для конфликтов.
